Wayfare: System Design

How the Wayfare prototype is built today, and the architecture it grows into for production. Version 1.1, October 2026.

Summary

Wayfare runs today as one self-contained HTML file: a WebGL globe, a single-page app and two data layers, with no backend. Inside Claude, an AI layer supplies details and itineraries; on any other website, a live open-data layer takes over automatically. The production version moves keys, data and AI calls behind a small backend and uses licensed sources throughout.

Goals and non-goals

Goals

  • Map-first discovery: from globe to a list of attractions within a chosen radius in two taps.
  • One attraction page that answers "should I go, and how" in under a minute.
  • Itineraries grounded in real opening hours, distances and weather.
  • Fast on mid-range phones: first paint under 2 seconds on 4G.
  • Clear provenance: every section says where its data comes from.

Non-goals for the first release

  • Selling hotels, tickets or parking directly (link out or use affiliate programs instead).
  • Street-level maps or navigation (hand off to the phone's map app).
  • Scraping social media for tips.

Prototype architecture

Globe rendering pipeline

The globe is two stacked canvases that share one orthographic projection: WebGL draws the Earth, and a 2D canvas draws everything people tap.

LayerTechnologyWhat it draws
BackgroundCSSStarfield and deep-space gradient
EarthWebGL fragment shader on a full-screen quadNASA day and night textures, sun shading, ocean glint, twilight band, atmosphere rim
OverlayCanvas 2D with D3 orthographic projectionCountry borders, city dots, search radius, attraction markers, labels
  • Shared math: the shader inverts the same rotation D3 uses, so markers sit exactly on the imagery.
  • Textures: NASA Blue Marble at 4096 x 2048 and Black Marble at 2048 x 1024, embedded as data URIs (about 1.1 MB).
  • Sharpness: mipmaps with a level of detail computed per pixel, which avoids shimmer and a seam at the date line.
  • Day and night: a fixed light keeps the visible side bright; live mode computes the real sun position from the current UTC time.
  • Fallbacks: no image support falls back to a procedurally painted Earth; no WebGL falls back to flat 2D colours.
  • Interaction: pointer events for drag and pinch, animated fly-to with a zoom dip, hit testing on the overlay.

AI layer (inside Claude)

In the prototype, Claude is the data source for anything that needs knowledge of a place, and the planner for itineraries. Every call returns strict JSON or streamed Markdown.

Reliability rules

  • A queue runs at most two calls at once, overview first, and drops queued calls when the user moves to another place.
  • Each section loads and fails on its own, with a retry button.
  • Responses are cached for an hour, so revisiting a place is instant.
  • With no AI available, the app serves offline demo data for Paris and the Eiffel Tower.
  • Prompts forbid invented quotes and URLs; uncertain fields come back empty.

Live open-data mode

Outside Claude, for example on this website, the prototype switches to live open data automatically, so every city and attraction works without a backend or API keys.

FeatureSourceHow it is used
Attractions in a radiusOpenStreetMap (Overpass)Places tagged as attractions, museums, viewpoints, worship sites and parks with a Wikidata link, ranked by how many languages name them
Details and historyWikipedia and WikidataSummary, dated history sentences, facts such as height, style, heritage status and visitors per year
PhotosWikimedia CommonsUp to 10 openly licensed photos taken nearby, each with author and license
Food, parking, transitOpenStreetMapRestaurants by cuisine, public parking and stations within a short walk
TipsWikivoyageGetting around, safety, etiquette and money advice for the city
WeatherOpen-MeteoReal 16-day forecast, four years of recorded history, sunrise and sunset for golden hour
SearchOpen-Meteo geocoding, WikipediaCities and landmarks suggested as you type
ItineraryBuilt-in plannerRanks attractions by interests, groups them into days by area, adds nearby restaurants and the forecast

Ratings and written reviews have no free open source, so the app links to Google, Tripadvisor and Yelp rather than copying them.

How the mode is chosen and kept reliable

  • If the page can reach Claude it uses the AI layer; otherwise it switches to open data at start-up, with no setting to change.
  • Every open-data call has a timeout, and the place search tries a second Overpass server if the first is busy.
  • Responses are cached in memory, so revisiting a city or attraction makes no new requests.
  • Each tab loads and fails on its own with a "Try again" button; Paris and the Eiffel Tower fall back to built-in sample data when offline.
  • The map library is bundled into the file, so the globe works behind strict security settings.

Production architecture

Data sources

Production replaces AI-compiled data with licensed sources. There are two viable stacks: a paid Google-centred one with the richest data, and a free, openly licensed one that costs only hosting.

Licensing rules that shape the design

  • Google place content must be shown on a Google map and must not be stored, except place IDs.
  • OpenStreetMap and Wikipedia require attribution and share-alike on derived data.
  • Every source gets a line on an in-app credits screen.
  • Prices and terms change often: re-check before launch, and have a lawyer review.

Security, privacy, scaling and risks

Security

  • All provider and AI keys live on the backend; the app ships no secrets.
  • Rate limits per user and per IP, plus daily spend caps in each provider console.
  • Prompts treat fetched web text and user tips as data, never as instructions.

Privacy

  • Location is used only when the user taps "Find me", and is not stored.
  • Trips and itineraries belong to the user and can be deleted in the app, as app stores require.
  • A plain-language privacy policy that includes each provider's terms.

Scaling and cost

  • Stateless API containers that scale with traffic; Postgres for user data only.
  • Cache what licences allow; request only the fields each screen needs, since provider prices rise with richer fields.
  • Cache itineraries for popular destinations and cap free itinerary runs per user to control AI spend.
  • Monitoring: crash reporting, request latency per provider, and a daily cost dashboard.
